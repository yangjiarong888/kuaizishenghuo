# 筷子生活 Appium 仓库审查与重构设计

## 目标

以当前 Git 仓库为唯一业务与结构基准，对登录、首页、商城、外卖、跑腿、充值及公共基础设施进行分阶段审查和保守重构。重构保持现有业务流程、公开入口和默认安全行为兼容，只修复有代码、日志、测试或真机证据支持的问题。

父目录中的旧脚本和历史日志只作为迁移与缺陷证据，不反向覆盖当前 Page Object、Flow 和测试设计。

## 已确认约束

- 采用分阶段纵向重构，不做全仓库一次性机械替换。
- 每阶段必须先建立离线测试基线，再修改实现，最后执行阶段回归。
- 所有缺陷修复遵循失败测试、最小实现、重构、回归的顺序。
- 最终必须执行真机验证。
- 真机回归默认无副作用：禁止提交订单、支付、发送验证码，以及新增、修改或删除地址、账户或其他业务数据。
- 敏感账号、密码、验证码和支付信息只能通过运行时安全输入或环境变量提供，不得写入源码、测试数据、文档、截图名称或日志。
- 当前环境无法直接调用 `git`；在 Git 恢复可用前，不得声称已提交设计或代码。

## 当前证据与风险

- 仓库约有 65 个 Python 文件，接近 1 MB 源码；多个文件超过 800 行。
- `scripts/run_mall_order_flow.py` 超过 3000 行，`pages/takeout_checkout_mixin.py` 超过 2800 行，登录 OAuth Mixin 超过 2300 行，职责边界过大。
- 商城、外卖和登录代码存在大量固定 `time.sleep`，容易产生慢执行和时序波动。
- 页面层大量使用宽泛异常捕获和多组兜底 XPath，部分关键失败可能被转换为不可诊断的 `False`。
- 现有测试主要覆盖跑腿和充值的 Fake Driver 行为；登录、首页、商城和外卖缺少相称的离线覆盖。
- `requirements.txt` 声明了 `pytest`，但当前虚拟环境未安装，尚不能建立完整测试基线。
- Appium 3.2.0 在 `http://127.0.0.1:4723` 可用；`adb` 当前不在 PowerShell PATH。
- 历史日志存在中文乱码，且曾出现搜索连续两次超时、第三次成功，说明等待与诊断策略需要治理。该日志仅作为风险证据，不作为当前仓库缺陷已复现的结论。

## 目标架构

### `commons`

统一配置、Driver 生命周期、显式等待、条件轮询、日志和失败证据采集。消除隐式等待与显式等待叠加，避免不同模块各自实现启动、重试和异常吞噬逻辑。

### `pages`

只负责稳定定位器、页面操作和页面状态判断。拆分过大 Page/Mixin，但通过兼容门面或原方法保留公开 API，避免调用方同时迁移。

### `flows`

负责业务步骤顺序、跨页面状态转换、分支决策和最终业务断言。Flow 不直接拼接定位器，不读取敏感配置。

### `scripts`

只解析命令行参数、读取环境变量、创建依赖、调用 Flow 并返回明确退出码。页面查找、点击和业务规则必须下沉到 Page 或 Flow。

### `testcases`

以离线 Fake Driver 单测为主，覆盖等待、分支、异常、安全开关和接口兼容性；真机用例单独标记并默认只运行无副作用路径。

## 实施阶段

本文件是仓库级总设计。为避免多个独立业务域在同一变更中共享风险，阶段 0 与阶段 1 使用独立实施计划；阶段 2 至阶段 6 分别使用独立实施计划和验收记录。只有前一阶段通过离线回归，下一阶段才可开始。阶段 7 只负责汇总验证，不引入新的重构。

### 阶段 0：环境与清理

创建并校验备份，清除已确认的旧脚本、缓存、误建目录和过期日志；恢复与 `requirements.txt` 一致的测试环境；建立静态与测试基线。

### 阶段 1：公共基础层

统一配置优先级、Driver 创建与关闭、App 启动模式、条件等待、日志和诊断产物。公开接口保持兼容，新增单元测试覆盖环境变量覆盖、Driver 复用与失败关闭路径。

### 阶段 2：登录与首页

将重复定位和状态判断收敛到小型助手，拆分过大的登录 Mixin 和 `pages/Home.py` 职责。保留现有入口、方法名和默认流程，不改变登录业务规则。

### 阶段 3：商城

按首页浏览、分类、商品详情、规格、购物车和订单预览拆分。`run_mall_order_flow.py` 退化为命令入口与编排器，订单提交保持显式安全开关，默认停在提交前。

### 阶段 4：外卖

按店铺、结算、配送时间和取消订单拆分；统一页面状态断言和等待条件。涉及订单创建或取消的路径默认不在真机安全回归中执行。

### 阶段 5：跑腿与充值

保留既有安全开关，强化输入校验、失败原因、状态断言和敏感信息脱敏。任何真实提交、支付或数据修改仍需用户逐次明确授权。

### 阶段 6：入口收口

清理脚本中的页面操作和重复业务逻辑，统一退出码、日志标签和依赖创建方式；保留现有可用命令入口的兼容包装。

### 阶段 7：全量验证

完成离线测试、静态检查、敏感信息扫描和真机无副作用回归。某阶段失败时只回退或修复当前阶段，不把多个领域的修复混在一次变更中。

## 等待、异常与诊断设计

- 用针对页面状态的显式等待或条件轮询替换可证明不必要的固定等待；动画节流等确需短暂停顿的场景保留并写明原因。
- 可选弹窗或可选元素允许返回“未出现”；页面进入、业务提交前置条件和最终状态等关键步骤必须明确失败。
- 宽泛异常仅允许出现在明确的边界层，并必须保留原始异常类型和上下文；不得用空 `except` 或静默 `pass` 掩盖关键失败。
- 失败证据至少包括当前 Activity、context、操作名称、脱敏定位信息和截图；需要 page source 时先执行敏感信息脱敏。
- 日志统一为 UTF-8，禁止记录账号、密码、验证码、支付信息和完整个人数据。

## 测试与真机验证

### 离线验证

- 公共层：配置覆盖、等待成功与超时、Driver 生命周期、日志脱敏和诊断触发。
- 页面层：定位器优先级、页面状态判断、可选元素与关键元素差异。
- Flow 层：步骤顺序、分支、失败短路、恢复行为和安全开关。
- 脚本层：参数解析、环境变量缺失、退出码和异常信息脱敏。
- 兼容性：现有公开类、方法和默认参数继续可用。

### 静态验证

- 全仓库 Python 语法编译和导入检查。
- 固定等待、裸异常、宽泛异常、重复定位器和超大文件的残留统计。
- 源码、测试、文档和日志中的敏感信息扫描。
- `requirements.txt` 与实际环境的一致性检查。

### 真机无副作用回归

- 首页启动与底部导航往返。
- 登录方式切换、忘记密码入口等不发送验证码的页面访问。
- 商城首页、分类、商品详情、规格和购物车展示，不提交订单。
- 外卖首页、店铺和结算前页面，不创建或取消订单。
- 跑腿菜单、地址选择页只读访问，不新增、编辑、删除地址或提交订单。
- 充值与生活缴费页面只读访问，不创建订单或支付。

每个流程记录明确的通过状态或环境性阻塞原因。不得通过放宽断言、吞掉异常或跳过关键步骤把失败伪装成通过。

## 验收标准

- 备份完整性检查通过，所有清理项具备可执行恢复方式。
- 离线测试全部通过且无敏感信息泄漏。
- 当前公开入口、类、方法和默认安全行为保持兼容。
- 已治理模块的固定等待、重复定位和宽泛异常显著减少，并有残留清单说明合理例外。
- 真机安全回归覆盖所有业务域，流程均有日志和截图证据；环境性阻塞被单独列出。
- 未经逐次授权，不产生订单、支付、验证码发送或业务数据变更。

## 非目标

- 不依据旧 `test.py` 重写当前业务流程。
- 不为追求文件行数进行无业务价值的机械拆分。
- 不修改 App 产品业务规则或服务端行为。
- 不在本轮执行真实下单、支付、验证码发送或数据删除。
- 不在 Git 不可用时伪造提交记录。
