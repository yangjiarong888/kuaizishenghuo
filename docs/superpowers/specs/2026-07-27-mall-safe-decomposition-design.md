# 商城安全拆分与分层真机验证设计

## 目标

把 `scripts/run_mall_order_flow.py` 从 3077 行的全职责脚本拆成可独立测试的网络、地址、购物车和结算模块，同时建立三层明确授权：

1. 默认严格零业务数据变化；
2. 显式允许购物车变更；
3. 显式允许创建和清理真实订单。

任何真实加购、地址变更、订单创建、支付、消息发送或订单取消都不得由默认参数触发。

## 已确认环境

- Android 设备 `21091116AC` 已连接，序列号为 `P7T4XC99CYAEYL4H`。
- Appium 3.2.0 已在 `127.0.0.1:4723` 就绪。
- 当前 App 前台 Activity 为 `com.idlefish.flutterboost.containers.FlutterBoostActivity`。
- 本设计阶段没有对设备执行点击、输入、启动、安装或业务数据变更。

## 现状与风险

- 商城脚本当前为 3077 行、124 个方法。
- 当前仍有 46 处固定等待和 50 处宽泛异常捕获。
- `--flow cart` 会真实加购并继续进入确认订单页。
- `--submit-order` 会创建真实订单。
- 支付方式只有 `cod` 和 `wechat_mock`；当前不支持真实微信手动支付。
- 货到付款订单创建后不会自动取消。
- 默认订单后 IM 行为可能向商家发送测试消息，属于独立业务副作用。
- 地址新增、编辑、复制已经要求 `--allow-address-mutation`，该边界继续保留。

## 设计方案

采用“先结构拆分、再按页面证据治理等待和异常”的方式。本轮不批量修改定位器、坐标兜底或结算状态判断，避免把机械迁移与行为变化混在同一提交中。

不采用：

- 一次性替换全部固定等待和宽泛异常，因为严格零业务数据变化真机路径无法覆盖地址、购物车和结算页面。
- 仅保留现有大脚本，因为后续每次定位器或业务顺序修改都会继续影响全部商城流程。

## 模块边界

### `flows/mall_order_http.py`

负责：

- JSON URL 请求；
- 库存响应解析；
- 订单状态响应解析；
- 模拟支付成功测试钩子；
- 嵌套 JSON 键查找。

该模块不依赖 Appium。网络调用通过可注入 opener 执行，以便离线测试成功、HTTP 错误、无效 JSON、缺少字段和超时分支。

### `pages/mall_order_address_mixin.py`

迁移地址页面识别、选择、搜索、填表、复制、编辑和保存方法。保留现有公开方法名和行为。

该模块所有写操作继续依赖已经验证的 CLI 双重授权：

- 具体地址动作参数；
- `--allow-address-mutation`。

本轮严格零业务数据变化真机回归不进入地址管理或地址编辑页。

### `pages/mall_order_cart_mixin.py`

迁移购物车打开、选择、管理、删除、减号和左滑逻辑。保留现有方法名。

所有会改变购物车的入口必须要求 `--allow-cart-mutation`，包括：

- `--flow cart`；
- `--add-to-cart-only`；
- `--run-cart-delete`；
- `--cart-delete-prepare-item`。

### `pages/mall_order_checkout_mixin.py`

迁移订单确认页金额、优惠券、备注、配送时间、订单提交、支付选择、库存断言、订单状态和订单后消息行为。

`MallOrderFlow` 继续作为兼容外观类，组合这些 mixin 并保留原脚本公开方法。

### `scripts/run_mall_order_flow.py`

只保留：

- CLI 解析；
- 参数安全校验；
- Driver 生命周期；
- Flow 初始化；
- 顶层业务分发；
- 明确退出码。

## CLI 安全模型

### 第一层：严格零业务数据变化

新增 `--verify-navigation-only`。

允许：

- 进入商城；
- 搜索商品；
- 打开商品详情；
- 读取名称、价格和页面标记；
- 采集截图和脱敏 page source；
- 返回。

禁止与以下参数组合：

- `--submit-order`；
- `--allow-cart-mutation`；
- 地址新增、编辑、复制或强制选择；
- 购物车删除；
- 库存不足提交；
- 断网异常流；
- 订单后 IM；
- 任何支付或订单取消参数。

校验在 Driver 创建前执行。

### 第二层：购物车变更

新增：

- `--allow-cart-mutation`；
- `--add-to-cart-only`。

`--add-to-cart-only` 只完成商品搜索、规格选择、数量选择和加购，验证购物车出现目标商品后停止，不进入结算。

该模式不会自动删除商品。执行结果必须记录目标商品名、SKU（若有）和数量，后续由用户决定人工清理或单独授权购物车删除。

现有 `--flow cart` 也必须显式传入 `--allow-cart-mutation`，否则在 Driver 创建前返回退出码 `2`。

### 第三层：真实订单

新增：

- `--allow-order-creation`；
- `--max-payable AMOUNT`；
- `--cancel-created-order`；
- `--allow-order-cancellation`。

真实提交必须同时满足：

- `--submit-order`；
- `--allow-order-creation`；
- `--max-payable` 为大于 0 的显式金额；
- 确认页实付金额不大于 `--max-payable`。

金额超过上限时必须在点击提交订单前失败。

`--cancel-created-order` 只有与 `--submit-order` 和 `--allow-order-cancellation` 同时使用时有效。取消前必须已解析并记录本次创建的订单号；取消失败时立即停止并报告需人工处理的订单号，不自动重复提交订单。

### 地址、消息和支付

- 地址写操作继续要求 `--allow-address-mutation`。
- 订单后 IM 默认关闭。若以后保留自动消息，必须新增 `--send-order-im` 和 `--allow-order-message` 双重授权；现有 `--skip-order-im` 可作为兼容参数，但不能让默认行为发送消息。
- `cod` 会创建真实货到付款订单，不代表零副作用。
- `wechat_mock` 只允许在明确的测试环境钩子中使用，必须配置模拟支付 URL。
- 本阶段不增加真实微信自动或手动支付；若以后需要，单独设计并再次授权。

## 业务流程

### 严格零业务数据变化

CLI 校验 → Driver → 商城入口 → 商品搜索 → 商品详情识别 → 脱敏证据 → 返回。

### 只加购

CLI 双重授权 → Driver → 商品搜索 → 商品详情 → 规格和数量 → 加购物车 → 验证购物车商品 → 停止。

### 真实货到付款订单

CLI 订单授权和金额上限 → 商品/规格 → 确认订单页 → 读取实付金额 → 上限校验 → 提交订单 → 解析订单号 → 订单状态断言 → 可选显式取消。

### 模拟微信支付

CLI 订单授权和金额上限 → 提交订单 → 选择微信 → 调用测试环境模拟支付钩子 → 订单状态和库存断言 → 可选显式取消。

## 错误处理

- 安全参数组合非法：Driver 创建前返回 `2`。
- 页面、网络或业务断言失败：返回 `1`。
- `--max-payable` 缺失、非数字或不大于 0：Driver 创建前返回 `2`。
- 确认页实付金额超过上限：业务流返回 `1`，且不点击提交。
- 订单号无法解析：不执行取消、不执行 IM，报告人工核查。
- 取消失败：输出脱敏诊断和订单号，禁止自动再次提交。
- 网络客户端只记录异常类型、URL 主机/路径模板或状态码，不记录 token、个人信息或完整敏感响应。

## 测试策略

### TDD 与离线测试

- CLI 参数默认值、互斥组合和 Driver 前校验。
- `--verify-navigation-only` 不调用加购、地址、提交、支付或取消。
- `--add-to-cart-only` 缺少能力参数时拒绝。
- 真实提交缺少能力或金额上限时拒绝。
- 金额等于上限允许，超过上限拒绝且不调用提交。
- 订单取消缺少独立授权时拒绝。
- 订单后消息默认不调用。
- HTTP 模块覆盖成功、HTTP 错误、无效 JSON、缺少字段和嵌套字段。
- mixin 迁移后运行公开流程的录制型测试，保护调用顺序和停止边界。

每批生产修改都必须运行：

- 对应聚焦测试；
- 完整 `pytest -m "not device"`；
- 全部 Python 内存编译；
- 固定敏感值扫描。

### 真机验证

第一阶段只执行 `--verify-navigation-only`，严格零业务数据变化。正常页面访问仍可能产生 App 自身的浏览统计或最近访问记录，自动化不创建购物车、地址、订单、支付或消息数据。

第二阶段真实加购只有在用户当次再次明确授权后执行；测试完成后不自动删除，除非用户同时授权购物车删除。

第三阶段真实订单只有在用户提供测试商品、支付方式、金额上限和当次明确授权后执行。任何真实支付仍需新的单独授权。

## 验收标准

- 默认 CLI 和 `--verify-navigation-only` 不改变购物车、地址或订单。
- 所有购物车变更都要求 `--allow-cart-mutation`。
- 所有真实订单都要求 `--allow-order-creation` 和显式金额上限。
- 订单后 IM 默认关闭。
- 自动取消要求独立授权，失败时可定位本次订单号。
- 原 `MallOrderFlow` 公开方法保持兼容。
- 完整离线测试零失败。
- 严格零业务数据变化真机路径通过后，才进入登录剩余治理。
