# 海运业务真实下单自动化设计

## 目标

根据录屏完善国际货运自动化，使用 `scripts/run_shipping_business.py` 作为独立执行入口，并扩展 `pages/shipping_page.py` 页面对象。脚本必须从筷子生活首页进入国际货运，覆盖海运首页与配送订单 Tab 切换、公共地址选择或新增、未来配送时间选择、真实订单提交、余额真实支付、货到付款、待支付取消及订单状态校验。

## 已确认范围

- 从筷子生活首页点击“国际货运”，不依赖执行前已停留在海运页面。
- 验证海运首页，并支持海运首页与配送订单列表 Tab 双向切换。
- 配送地址使用与外卖共用的公共地址簿。
- 地址既可选择已有记录，也可新增后选择。
- 配送日期必须严格晚于设备当天；当天不可选。
- 提交真实订单。
- 支持余额真实支付和货到付款。
- 待支付订单可以取消支付；已支付订单不能取消支付。
- 输出可诊断日志，同时保护支付密码和完整地址等敏感数据。
- 不自动取消已完成支付或货到付款的订单。

## 不在范围内

- 不修改外卖现有业务行为。
- 不批量创建、批量支付或批量取消订单。
- 不使用固定屏幕坐标作为主定位方式。
- 不在源码、命令行参数或日志中保存支付密码。
- 不自动取消已支付订单，也不验证退款流程。

## 文件与职责

### `scripts/run_shipping_business.py`

独立命令行入口，负责：

- 解析场景、支付方式、地址策略、会话名和驱动关闭参数。
- 从环境变量读取支付密码和新增地址数据。
- 在任何页面点击前完成参数与秘密信息校验。
- 创建或复用 `DriverManager` 会话。
- 调用 `ShippingPage` 执行业务流并用进程退出码报告结果。

### `pages/shipping_page.py`

海运页面对象，负责：

- 从 App 首页进入国际货运。
- 识别海运首页、配送订单列表、提交订单、支付页和订单详情。
- 在海运首页与配送订单 Tab 之间切换并校验落地页面。
- 处理公共地址簿、配送日期、订单提交、支付和状态断言。
- 在失败时调用项目诊断能力保存截图和页面 XML。

### `testcases/test_shipping_page.py`

使用假 Driver 测试业务决策和交互顺序，避免单元测试产生真实订单。重点覆盖日期、地址、状态机、重复提交保护和秘密信息预校验。

### `testcases/test_package_cli.py`

测试命令行参数组合、默认值、环境变量读取、非法组合及退出码。

## 页面导航

### 首页入口

1. 确认当前位于筷子生活首页；必要时使用现有首页恢复能力。
2. 优先通过可见文本或资源 ID 定位“国际货运”。
3. 点击后等待海运首页强标志，而不是仅凭包含“海运”的模糊文本判定成功。
4. 入口失败时记录当前 Activity、可见文本、截图和 XML。

### 海运 Tab

页面对象提供两个明确动作：

- `switch_to_shipping_home()`：点击海运首页 Tab，并验证首页服务入口或首页标题。
- `switch_to_delivery_orders()`：点击“配送订单”Tab，并验证订单列表标题、状态筛选或订单卡片。

每次切换后重新查找元素，不复用切换前的元素引用。完整流程结束后再做一次 Tab 往返检查，确认两侧都可达。

## 公共地址流程

命令行参数 `--address-policy` 支持：

- `auto`：默认。优先选择匹配的已有地址；未找到时新增地址。
- `existing`：只选择已有地址；未找到则在提交订单前失败。
- `add`：强制新增地址，保存后选择新增记录。

新增地址通过以下环境变量提供：

- `SHIPPING_ADDRESS_MATCH`（已有地址匹配关键字，可取姓名、电话末四位或地址摘要）
- `SHIPPING_ADDRESS_NAME`
- `SHIPPING_ADDRESS_PHONE`
- `SHIPPING_ADDRESS_COUNTRY`
- `SHIPPING_ADDRESS_CITY`
- `SHIPPING_ADDRESS_DETAIL`
- `SHIPPING_ADDRESS_POSTCODE`

使用 `existing` 时必须提供 `SHIPPING_ADDRESS_MATCH`；使用 `auto` 但未提供匹配关键字时，直接进入新增地址分支，不盲选第一条公共地址。使用 `auto` 且需要新增、或使用 `add` 时，所有页面必填字段必须在任何保存动作前校验。已有地址匹配优先使用姓名、脱敏电话尾号与地址关键字。

选中或新增地址后必须回到提交订单页，并回读姓名、电话尾号或地址摘要中的至少两个稳定标志。未回填、地址不可配送或页面仍显示“请选择地址”时终止流程。

公共地址交互规则与外卖保持一致：支持 Flutter 地址弹层、滚动查找地址行、选择已有地址和新增地址页。实现可以提取无业务差异的地址识别工具，但不得为了本任务改变外卖下单语义。

## 配送日期规则

1. 打开配送时间选择器并收集所有可点击日期与时间段。
2. 日期解析以设备当天为基准，支持“明天”“后天”、`M月D日` 和包含年份的日期。
3. 过滤掉当天、过去日期、禁用日期和无法解析日期。
4. 从剩余候选中选择最早日期，再选择该日期下第一个可用时间段。
5. 确认选择后回读提交订单页的配送时间。
6. 回读日期必须严格大于当天，否则在提交前失败。

不允许在解析失败时退化为选择第一个日期，也不允许通过固定索引假设第二项一定是明天。

## 订单与支付状态机

### 余额正常支付

1. 地址与未来配送时间校验通过。
2. 点击一次“提交订单”，进入支付页或获得订单号。
3. 选择余额支付。
4. 从 `SHIPPING_PAY_PASSWORD` 读取支付密码并输入。
5. 确认真实支付。
6. 验证订单详情存在订单号，且状态不含“待支付/待付款”。
7. 验证“取消支付”入口不存在或不可用；不通过坐标尝试点击隐藏区域。

### 货到付款

1. 地址与未来配送时间校验通过。
2. 选择货到付款并提交真实订单。
3. 验证订单详情支付方式为货到付款，订单状态符合已创建状态。
4. 货到付款不读取支付密码，也不执行取消支付。

### 待支付取消

1. 使用余额支付提交真实订单，但在确认扣款前退出支付流程。
2. 验证订单状态明确为“待支付/待付款”。
3. 只有状态明确匹配时才点击“取消支付”。
4. 处理确认弹窗并验证订单不再保持可支付状态，或页面明确显示取消结果。

### 状态保护

- 已支付、货到付款或状态无法识别时，禁止点击“取消支付”。
- 提交按钮点击后立即进入等待状态；支付页、订单号、加载状态任一出现后均不得再次点击提交。
- 页面长时间无响应时保存诊断证据并失败，不以重复点击作为恢复策略。
- 支付密码缺失或支付方式非法时，在进入订单页和产生真实订单之前失败。

## 命令行设计

建议入口：

```text
python scripts/run_shipping_business.py --payment-method balance --address-policy auto
python scripts/run_shipping_business.py --payment-method cod --address-policy existing
python scripts/run_shipping_business.py --payment-method balance --cancel-unpaid --address-policy add
```

参数：

- `--payment-method {balance,cod}`，默认 `balance`。
- `--cancel-unpaid`，仅允许与 `balance` 组合。
- `--address-policy {auto,existing,add}`，默认 `auto`。
- `--session`，默认 `shipping_business`。
- `--quit-driver`，流程结束后关闭当前脚本会话。

`--cancel-unpaid` 与 `cod` 同时出现时，命令行校验失败且不创建 Driver。

## 日志与诊断

日志必须包含：

- 首页入口和 Tab 切换结果。
- 地址策略、选择已有或新增、地址回填校验结果。
- 候选配送日期、被过滤原因和最终选中的未来日期。
- 支付方式、订单号、订单状态和取消支付结果。
- 异常类型、失败阶段和诊断文件路径。

敏感信息处理：

- 支付密码仅记录“已配置/未配置”，绝不记录内容或长度。
- 电话仅记录国家码和末四位，其余掩码。
- 详细地址仅记录用于匹配的非敏感摘要，不输出门牌等完整信息。
- 不把秘密信息写入截图名、XML 文件名或异常文本。

## 错误处理

以下情况必须在提交订单前失败：

- 未从 App 首页进入国际货运。
- 海运首页或配送订单 Tab 无法验证。
- 地址策略需要新增但必填数据不完整。
- 地址未成功回填或明确不可配送。
- 没有严格晚于当天的配送日期。
- 日期选择后回读结果仍为当天、过去日期或不可解析。
- 余额正常支付场景未配置 `SHIPPING_PAY_PASSWORD`。

订单提交后的失败必须保留订单号（如可获取）、当前状态、截图和 XML，便于人工处理可能遗留的真实订单。

## 测试策略

采用测试驱动开发，先观察测试因缺少行为而失败，再实现最小代码使其通过。

单元测试至少覆盖：

- 从首页点击国际货运，并验证海运首页。
- 海运首页与配送订单 Tab 双向切换。
- `auto` 优先已有地址，未找到时新增。
- `existing` 找不到地址时失败且不提交。
- `existing` 缺少匹配关键字时在创建 Driver 前失败。
- `add` 缺少字段时在任何页面点击前失败。
- 地址保存后必须回填验证。
- 当天、过去日期、禁用日期和不可解析日期被拒绝。
- 选择最早未来日期并回读复核。
- 提交按钮只点击一次。
- 余额支付缺少密码时预校验失败。
- 余额支付成功后禁止取消支付。
- 待支付状态允许取消支付。
- 未知状态禁止取消支付。
- 货到付款不读取密码且不执行取消支付。
- 日志不包含支付密码、完整电话和完整详细地址。
- CLI 非法参数组合不创建 Driver。

验证分层：

1. 运行新增单元测试，确认红灯原因是功能尚未实现。
2. 实现后运行海运相关测试。
3. 运行完整 `pytest` 回归，确认未影响首页、外卖、商城和跑腿流程。
4. 在真实设备上先运行不产生订单的页面导航与 Tab 探测。
5. 仅在环境变量、地址数据和 Appium 状态均满足时运行用户授权的真实订单场景。

## 验收标准

- `scripts/run_shipping_business.py` 能从 App 首页进入国际货运。
- 海运首页和配送订单 Tab 均可识别并往返。
- 公共地址可按策略选择已有地址或新增地址，并验证回填。
- 选中的配送日期严格晚于设备当天。
- 余额支付能真实扣款并验证已支付状态。
- 货到付款能创建真实订单并验证支付方式。
- 待支付订单可以取消支付，已支付订单不能取消支付。
- 重复提交、秘密泄漏和未知状态误取消受到保护。
- 日志与诊断证据足以定位失败阶段。
- 新增测试和完整回归测试通过后，才可声明实现完成。
