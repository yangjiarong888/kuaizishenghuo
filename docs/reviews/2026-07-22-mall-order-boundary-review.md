# 商城订单边界审查与第一轮重构报告

## 审查结论

- 商城入口默认不提交订单，也不创建、编辑、复制或强制选择地址。
- 地址变更现在必须同时提供具体动作参数和 `--allow-address-mutation`；校验发生在 Driver 创建之前，非法组合返回退出码 `2`。
- 收货人、手机号、微信号、地址搜索词和详细地址不再使用源码固定值，只能来自显式命令行参数或 `MALL_TEST_ADDRESS_*` 环境变量。
- 金额解析、数值容差和订单快照已移入无 Appium 依赖的 `flows/mall_order_types.py`；原商城脚本继续重导出这些名称，保持现有导入兼容。
- 金额解析不再接受 `￥12.345`、`PHP 1.2.3` 这类格式的部分匹配结果。

## 验证证据

- 商城 CLI 聚焦测试：`8 passed`。
- 商城类型与 CLI 联合测试：`24 passed`。
- 完整离线测试：`146 passed, 1 deselected`，零失败。
- Python 内存编译：`81` 个 `.py` 文件全部成功。
- 商城脚本从计划基线的 `3097` 行降至 `3077` 行；纯订单类型已脱离 UI 自动化依赖。
- 商城地址默认值扫描仅命中空值环境变量读取、参数绑定和授权校验，未发现固定姓名、手机号、微信号或街道地址默认值。

## QA 风险判断

- 当前变更保护的是“默认无副作用”和“纯金额边界”，没有验证真实商品、优惠券、库存、收银台或订单状态接口。
- `scripts/run_mall_order_flow.py` 仍有 `3077` 行、`124` 个方法、`46` 处固定等待和 `50` 处宽泛异常捕获，仍属于高耦合高维护风险文件。
- 宽泛异常可能把可选元素缺失、页面状态错误和 Driver 故障混为同一分支；固定等待仍可能导致真机慢环境误判和快环境空耗。
- 全仓安全扫描另发现 `pages/takeout_checkout_mixin.py` 的支付密码参数仍以 `"123456"` 为生产默认值。这不是商城阶段引入的问题，但属于后续外卖域的高优先级安全边界，必须改为显式参数或环境变量，并在 Driver/支付动作前校验。
- 长数字扫描的其余命中主要位于脱敏测试夹具、充值页测试数据和登录示例；是否为真实业务数据不能仅凭静态扫描判断，后续按业务域逐项复核。

## 下一步

1. 外卖域：先移除支付密码默认值，再拆分结算、配送时间和订单取消职责。
2. 跑腿与充值域：复核提交/支付开关、账号测试数据、异常吞没和状态断言。
3. 登录 OAuth、首页与商城剩余大文件：结合真机页面状态逐段替换固定等待和宽泛异常。
4. 所有业务域离线回归完成后，统一执行真机无副作用验证；默认不下单、不支付、不发送验证码、不增删改业务数据。
